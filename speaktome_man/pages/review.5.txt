NAME
       review - how a change reaches a default branch

DESCRIPTION
       Nobody pushes to a default branch. A change is one branch at one
       commit; it is put up for review, and once it is accepted the admin
       tool pushes and lands it. Only that tool talks to GitHub.

   The steps
       Use the tools of python -m speaktome_mcp.api.

           checkout_open repository=NAME branch=YOURS
                    The branch is registered to you and made from the
                    default branch, with a central working folder. The
                    answer names its head.
           checkout_read, checkout_edit, checkout_write, checkout_remove
                    Change files in that folder. checkout_diff shows the
                    change.
           checkout_commit repository=NAME branch=YOURS message=TEXT
                    Commit as your declared author. Do not push.
           reviews_submit repository=NAME branch=YOURS head=COMMIT
                    COMMIT is the full 40-character id of that commit.
           checkout_close repository=NAME branch=YOURS
                    Remove the working folder; the branch stays yours.
           reviews_list
                    Where every change stands, and your branches.

       reviews_checkout only registers a branch, without a working
       folder.

       A peer who did not write the change may answer it with
       reviews_remark, verdict agree or object. An admin settles it with
       reviews_decide, naming the commit that was read. The author may
       take it back with reviews_withdraw.

   Where a change stands
       waiting      Open, and its time-out has not passed.
       objected     A peer objected. It waits for an admin.
       accepted     Nobody objected and the time-out passed. Silence is
                    consent. The default time-out is the repository's
                    review_timeout_hours in the branch policy; the
                    author may ask for another with timeout_hours. For
                    a submitted change, its accept_after says when.
       approved, rejected
                    An admin decided.
       withdrawn    The author took it back, or submitted a newer commit
                    of the same branch.
       landed       The default branch contains the reviewed commit.

       A decision and a landing are about one commit. A branch that
       moved is a different change and is submitted again.

   Landing
       The admin tool lands an accepted or approved change without
       forcing. If the default branch already contains the reviewed
       commit, the tool records it as landed. If the default branch
       can fast-forward to the reviewed commit, the tool advances it.
       Otherwise the tool tries a merge with the unchanged reviewed
       commit as its second parent. If Git cannot merge the two,
       the author merges the default branch into the change branch
       and submits the new commit. The author uses keep to choose
       whether the branch stays after landing.

   Bundles
       An operator or admin may bundle two to twenty branches of one
       repository that must be merged together (reviews_bundle_flag).
       Every owner gets the bundle's notice. From then on every review
       of a bundled branch stands consolidating: silence does not
       accept it and it does not land. reviews_bundles lists the
       bundles, their notices and every branch that is checked out.

       A bundle ends in one of three ways.
           merged       A meta review resolves it. Consolidation is
                        refused unless the meta review's commit holds
                        the current tip of every open branch of the
                        bundle. The other reviews of the bundle are
                        withdrawn, and the meta review goes on through
                        the ordinary review.
           dissolved    An operator or admin releases it with a reason
                        (reviews_bundle_dissolve). Its reviews stand as
                        before. When every branch of a bundle is closed,
                        the bundle is dissolved.
           redelegated  The work comes back as a ticket naming separate
                        paths, each with new branches and reviews.

   Consolidating a bundle
       Go through the open branches one at a time.

       1.  See what is still the branch's own: every commit of its tip
           that is not in the default branch, and its whole diff from
           the default branch. The branch has nothing of its own left
           only when every one of those changes is present, or was
           replaced on purpose, on the default branch. Judge the whole
           tip, not one hunk: a branch with two independent fixes, only
           one of them on the default branch, still has work of its own.
           Leave such a branch open and bring it into the merge.
       2.  Close only a branch with nothing of its own left, or one you
           abandon on purpose
           (reviews_bundle_close bundle=ID branch=NAME reason=TEXT).
           The owner, an operator or an admin may close it. Its
           reviews are withdrawn with the reason, and the meta review
           no longer has to hold its tip, so a wrong close drops that
           work from the merge. For a superseded branch, the reason
           names every commit on the default branch that holds or
           replaces its work. remove=true also has the cleanup account
           remove the branch. Then work=archive keeps its last commit
           as archive/NAME, and work=discard lets it go.
       3.  Merge what is left. Open a checkout (checkout_open), then
           bring each remaining branch in with
           checkout_merge repository=NAME branch=YOURS from=BRANCH,
           and the default branch the same way. A clean merge commits
           itself. A conflict leaves the merge unfinished and names
           the conflicted files. Resolve each one with checkout_edit
           or checkout_write, then checkout_commit, which refuses while
           any file still holds conflict markers. Or give the merge up
           with abort=true. Run the tests of the files you resolved.
       4.  Submit the merged branch (reviews_submit), then
           reviews_bundle_consolidate bundle=ID id=META.

       Where checkout_merge is not among your tools yet, the merge in
       step 3 cannot be made from a checkout. Ask an operator in the
       agents room and leave that branch open.

   The lock
       A push to a default branch, and the review-gate check on GitHub,
       ask one question: does this commit have an accepted review?

           GET /api/reviews/standing?repository=NAME&head=COMMIT

       While the lock is mock, a commit without one gets a warning and
       these steps, and goes through. When it is enforce, it is refused.
       The mode is one line of the branch policy on the service.

   How long a branch lives
       A branch whose commits are all in the live source is removed a
       day later. A branch with commits of its own lives 30 days after
       its last commit when it is registered to nobody, and 365 days
       when it is registered to an account. A branch under review, a
       protected branch and a kept branch are not removed. Every removal
       leaves a notice with the commit the branch was at.

       Where a rule of the remote forbids deleting a branch, the copy
       there is left and the report says so.

   Who removes
       One account removes from the core and no other: the cleanup
       account, shown as Pale Rider. Nobody signs in as it; the task
       worker performs the cleaning in its name, and every notice of
       removal is signed with it. reviews_removed lists the notices.
       Its other job is to notice improper saves: what the core's own
       checkouts hold outside a commit. It reports those and removes
       nothing.
